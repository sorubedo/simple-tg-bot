# 设计取舍

本文件记录已经做出的设计决定、原因和代价。改代码前先确认没有推翻这些前提。若确实需要改变，先改本文件并说明迁移方案。

## 1. 只服务一个超级群组

**决定**：一个 Simple-TG-Bot 进程只绑定 `telegram.group_id` 指定的一个超级群组。动作协议中没有 `chat_id` / `group_id`。

**原因**：

- 业务程序不应该有能力误操作其他聊天。
- 去掉群组参数后，钩子程序和动作 JSON 都更简单。
- 单群组边界让“目标群组校验”成为启动时的硬条件。

**代价**：需要管理多个群组时，要运行多个 Simple-TG-Bot 实例，并分别配置 token 或权限。

**代码位置**：`config.py` 的 `group_id` 校验，`bot.py` 的 `classify_target_chat`，`actions.py` 不接受 `chat_id`。

## 2. 无状态，不持久化

**决定**：不使用数据库、会话文件、PTB persistence、动作队列持久化或业务状态存储。更新 offset 和动作队列只在内存中。

**原因**：

- Simple-TG-Bot 只做传输和调度，业务状态归钩子程序所有。
- 没有数据库迁移、备份和并发写入问题。
- 重启行为可预测：Simple-TG-Bot 从 Telegram 重新拉取未确认更新。

**代价**：

- 重启后未确认的更新可能重复投递，钩子程序可能再次运行。
- 关机时未执行的动作会丢失。
- 需要去重或历史时，钩子程序必须自己保存。

**代码位置**：`bot.py` 不挂载 persistence，`action_queue.py` 使用内存 `asyncio.Queue`。

## 3. 钩子程序是外部进程，不是导入的插件

**决定**：每个程序通过 `asyncio.create_subprocess_exec` 启动，事件走 stdin，动作走 stdout。程序可以用任意语言。

**原因**：

- 业务代码和 bot 进程隔离。程序崩溃、内存泄漏或依赖冲突不会拖垮主进程。
- 不需要为插件定义 Python 接口，也不会把业务对象带进主进程。
- 语言无关，Shell、Go、Rust 都可以接入。

**代价**：

- 每次事件都有进程启动开销。高频消息场景应合并程序或使用更轻量的可执行文件。
- 不能直接共享内存，程序之间只能通过外部状态协作。
- 程序必须自己处理超时和输出格式。

**代码位置**：`programs.py` 的 `ProgramRunner`。

## 4. 动作协议没有 `chat_id`

**决定**：动作只描述“做什么”，不描述“在哪里做”。目标群组由 Simple-TG-Bot 在启动时确定。

**原因**：

- 这是第 1 条的直接结果，也是最重要的安全边界。
- 程序不需要知道群组 ID，示例脚本可以直接复用。

**代价**：无法通过动作向其他聊天发消息。这是有意限制，不是遗漏。

## 5. 动作串行执行，有界队列，背压

**决定**：只有一个 action worker，FIFO 执行动作组。队列有上限，满了让生产者等待，超时后整组拒绝。

**原因**：

- 避免多个动作同时调用 Telegram，降低触发限流和顺序错乱的概率。
- 顺序确定，便于理解和排查。
- 有界队列防止慢网络导致内存无限增长。

**代价**：吞吐量受单个 worker 限制。慢动作会拖慢后续动作。需要高吞吐时应拆分实例或减少动作。

**代码位置**：`action_queue.py`。

## 6. 消息更新串行处理

**决定**：PTB 的 `concurrent_updates(False)`，更新队列有界，消息钩子按配置顺序执行。

**原因**：

- 慢钩子形成背压，而不是并发产生不可预测的副作用。
- 多个程序对同一条消息的处理顺序固定。

**代价**：一个慢程序会延迟后续所有消息。通过 `timeout_seconds` 和 `polling.max_pending_updates` 控制最坏情况。

## 7. 动作组全有或全无

**决定**：stdout 解析要么返回完整动作列表，要么抛错。入队以整个动作组为单位，不会部分入队。

**原因**：

- 避免“前半组执行了、后半组丢了”的隐蔽状态。
- 程序可以放心地把相关动作放在一个数组里。

**代价**：一个字段写错会导致整组被丢弃。日志必须清楚指出错误字段。

**代码位置**：`actions.py` 的 `parse_actions`，`action_queue.py` 的 `enqueue`。

## 8. 动作字段从触发上下文取默认值

**决定**：消息钩子中省略 `topic_id` 时使用触发话题，省略 `message_id` 时使用触发消息。启动/关闭钩子没有消息上下文。

**原因**：

- 大多数回复、删除、贴表情都针对触发消息，省略参数可以减少样板代码。
- 显式 `null` 可以强制发到 General，保留控制力。

**代价**：默认值依赖钩子类型。在 General 或启动/关闭钩子中，话题动作必须显式提供 `topic_id`，否则报错。

**代码位置**：`actions.py` 的 `ActionContext` 和 `_resolve_*` 函数。

## 9. 失败隔离，不自动重试程序

**决定**：程序启动失败、超时、退出码非 0、stdout 非法，只记录日志并继续下一个程序。Simple-TG-Bot 不自动重试程序。

**原因**：

- 程序失败的原因可能是配置、代码或外部依赖，盲目重试会放大问题。
- 一条消息的失败不应该阻塞整个群组的其他处理。

**代价**：失败的消息不会自动补处理。需要重试时，由程序自己实现，或等待下一条匹配消息。

## 10. 显式发送 `allowed_updates`

**决定**：配置为 `null` 时，Simple-TG-Bot 仍然向 Telegram 发送空数组，而不是省略参数。

**原因**：

- Telegram 会记住上一次的 `allowed_updates`。省略参数可能继承其他工具或旧运行留下的集合。
- 显式发送空数组表示“使用默认集合”，行为可预测。

**代价**：如果用户想限制更新类型，必须显式写数组，并确保包含程序订阅的类型。

**代码位置**：`bot.py` 调用 `updater.start_polling(allowed_updates=...)`。

## 11. stdout 只放动作，stderr 放诊断

**决定**：动作 JSON 是 stdout 的唯一内容。程序日志、警告和调试信息必须写 stderr。

**原因**：

- 解析器可以严格校验 stdout，不需要猜测哪些行是日志。
- 失败时 stdout 整体丢弃，语义简单。

**代价**：程序不能把普通打印混进 stdout。很多语言的默认日志输出需要显式改到 stderr。

## 12. 动作结果不回传

**决定**：动作异步执行，程序退出后不会收到成功或失败结果。

**原因**：

- 程序是短生命周期进程，动作可能在程序退出后才执行。
- 回传结果需要额外的 IPC、状态和超时设计，和“无状态”目标冲突。

**代价**：需要结果时，程序必须查看日志或自己维护外部状态。例如 `create_topic` 的新话题 ID 只写入日志。

## 13. 关闭顺序：先停更新，再跑 shutdown，再排空

**决定**：收到信号后停止轮询，等待已接收消息处理完，执行 `shutdown` 钩子，最后在超时内排空动作队列。

**原因**：

- 先停更新，避免关闭钩子和消息钩子竞争。
- 关闭钩子执行时 Telegram API 仍可用，可以发送告别消息。
- 最后排空队列，保证关闭钩子的动作也有机会执行。

**代价**：积压消息多且钩子慢时，关闭会变慢。极端情况下排空超时，未执行动作被丢弃。

## 14. Telegram 日志通道独立于更新和动作队列

**决定**：日志有独立的有界缓冲和后台任务，不经过 action queue。

**原因**：

- 发送日志本身可能失败或触发限流，不能让它阻塞业务动作。
- 避免“发送日志产生日志再发送”的反馈循环。

**代价**：日志可能延迟、聚合或在高负载时丢弃最旧记录。日志顺序不完全等同于 stdout。

## 15. 配置严格校验，未知键报错

**决定**：所有层级拒绝未知键，类型和范围严格检查。

**原因**：

- 拼写错误不会被静默忽略。
- 配置是主要接口，错误应在启动时暴露，而不是运行中才发现。

**代价**：升级版本时如果新增或重命名字段，旧配置可能需要调整。

## 16. 选择 python-telegram-bot 22.8

**决定**：使用 `python-telegram-bot==22.8` 和 `json5==0.17.3`。

**原因**：

- 项目固定 Python 3.15.2。搭建时 `aiogram` 的 `requires-python` 上限低于 3.15，无法安装。
- PTB 原生 asyncio，提供长轮询、更新队列、handler、生命周期和优雅关闭。
- 使用 bot token，不需要 MTProto 的 `api_id` / `api_hash` 和会话文件。
- 裸 `httpx` 需要自己实现 offset、重试、生命周期和信号处理，现阶段不值得。

**代价**：依赖 PTB 的更新队列和 handler 行为。升级大版本时需要重新验证。

## 17. `sleep` 只延迟动作队列

**决定**：`sleep` 由 action worker 执行，只暂停后续动作。

**原因**：

- 程序可以用一个动作数组表达“等一会儿再发下一条”。
- 不阻塞更新接收，也不影响同一钩子的下一个程序启动。

**代价**：不能用来延迟程序本身，也不能保证精确时间。

## 18. 不提供话题列表

**决定**：Simple-TG-Bot 不保存话题列表，也不提供列出话题的动作。

**原因**：Telegram Bot API 没有列出所有话题的接口。

**代价**：需要话题列表、名称到 ID 的映射时，钩子程序必须自己保存。

## 19. 附件随 `message` 事件，不新增钩子

**决定**：图片、文件、语音等媒体消息继续触发 `message` / `edited_message`，事件中增加 `message.attachments` 数组和 `message.media_group_id`。不增加 `photo`、`document` 或 `media` 钩子。

**原因**：

- 在 Telegram 中，带图片或文件的消息仍然是一条普通消息，有统一的 `message_id`、话题、发送者、回复关系和编辑语义。
- 新增钩子会让 `message` 过滤、去重、编辑处理和生命周期都要复制一份，程序也要同时订阅多个钩子。
- 现有程序只读 `message.text` / `message.caption`，忽略新字段即可继续工作；这是向后兼容的事件扩展。
- 一条消息最多包含一个逻辑附件。相册是共享 `media_group_id` 的多条消息，不需要把多条消息合并成一个大事件。

**代价**：

- 只处理文本的程序也会被媒体消息触发，需要自己检查 `message.text` 或 `attachments`。示例程序已经这样做。
- 照片有多个尺寸，协议只暴露最大尺寸。需要其他尺寸时必须通过 `file_id` 自行调用 Bot API。

**代码位置**：`programs.py` 的 `_attachments_payload` 和 `_message_payload`。

## 20. 附件下载显式开启

**决定**：默认只把附件元数据写入事件。只有程序配置 `message.download_attachments: true` 时，Simple-TG-Bot 才在启动程序前把附件下载到临时目录，并通过 `local_path` 暴露路径。

**原因**：

- 大多数钩子只需要判断消息类型，或直接把 `file_id` 交给 `send_photo` / `send_document` 复用，不需要文件字节。
- 无条件下载会增加每条媒体消息的延迟、网络流量和磁盘占用，而且会放大慢下载对串行消息处理的影响。
- 按程序开启可以只让真正需要文件的程序承担下载成本；同一消息的其他程序仍然立即启动。
- 临时目录在程序退出后删除，不引入持久化状态。

**代价**：

- 下载发生在串行处理链上，慢下载会延迟后续消息。单次 `getFile` 和实际下载分别受程序 `timeout_seconds` 限制。
- 下载失败不会跳过程序，程序必须检查 `download_error`。
- 同一媒体消息被多个开启下载的程序处理时会重复下载。

**代码位置**：`config.py` 的 `MessageHookConfig`，`programs.py` 的 `_download_attachments`。

## 21. 项目改名与协议提升到 /2

**决定**：发行包、Python 包和命令行入口分别改为 `simple-tg-bot`、`simple_tg_bot`、`simple-tg-bot`。环境变量改为 `SIMPLE_TG_BOT_CONFIG` 和 `SIMPLE_TG_BOT_TOKEN`。钩子事件中原有的应用信息字段改为 `bot`，事件和动作协议字符串分别改为 `simple-tg-bot.hook/2` 和 `simple-tg-bot.actions/2`。

**原因**：

- 旧名称同时出现在包名、入口点、环境变量、日志和协议中，只改显示名称会让外部接口继续暴露旧品牌。
- 事件中的应用信息字段被重命名，属于不兼容的协议变更，按协议演进规则必须提升版本号。
- 项目尚未发布稳定版本，直接切换到新命名空间比维护双协议更简单。

**迁移**：

- 钩子程序改为读取 `event["bot"]["version"]`。
- 需要校验协议的程序改用 `simple-tg-bot.hook/2`；动作 JSON 可以省略 `protocol`，或写 `simple-tg-bot.actions/2`。
- 部署脚本改用 `simple-tg-bot` 命令和 `SIMPLE_TG_BOT_*` 环境变量。
- 旧协议字符串不再被接受。

**代价**：

- 这是破坏性重命名，旧钩子和部署脚本必须同步修改。
- 应用版本从 0.3.0 提升到 0.4.0。

**代码位置**：`pyproject.toml`、`config.py`、`programs.py`、`actions.py`、`cli.py`。

## 22. 不做的事不是漏洞

以下功能明确不在当前范围。不要因为“看起来简单”就顺手加上：

- 多群组、Webhook、数据库、动作持久化。
- 投票、位置、联系人等非媒体消息的发送。
- 编辑消息内容（只接收 `edited_message` 通知）、转发、置顶、复制消息。
- 自定义 emoji 反应、多反应。
- 并行执行程序或多 worker 动作队列。
- 把动作结果回传给程序。
- 对非 `RetryAfter` 错误自动重试。

新增这些功能会改变协议或运行模型，必须先讨论并更新本文件。

## 主要代价汇总

| 选择 | 得到 | 放弃 |
| --- | --- | --- |
| 外部进程 | 隔离、语言无关 | 每次调用有进程开销 |
| 单群组 | 安全边界清晰 | 多群组要跑多实例 |
| 无状态 | 简单、可重启 | 可能重复处理，动作会丢 |
| 串行队列 | 顺序确定、易排查 | 吞吐受单 worker 限制 |
| 严格配置 | 错误早暴露 | 配置升级需要维护 |
| 动作全有或全无 | 不会半组执行 | 一个字段错整组丢弃 |
| 不回传结果 | 协议简单 | 程序要自己查状态 |
| 独立日志通道 | 不阻塞业务 | 日志可能延迟或丢弃 |
| 附件复用 message 钩子 | 协议和生命周期统一 | 文本程序也会被媒体消息触发 |
| 附件下载按程序开启 | 默认无下载延迟 | 需要文件时要显式配置并处理失败 |
